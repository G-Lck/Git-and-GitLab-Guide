Git Survival Guide

Common Git tasks, and what to do when things go gloriously sideways

Git is much less mysterious when you know which repository and branch you are in. When in doubt, start with git status. Think of it as asking Git, "So, what have we done?" before either of you makes things worse.

$ git status

Actions

The usual Git moves

Five common tasks, one step at a time. Run the commands from inside the project folder unless the instructions say otherwise. Git is powerful; it is not psychic.

Action 1
Create a new repository

Create an empty project on GitLab first, then connect your local folder to it. Replace the example URL with the SSH URL shown by GitLab. The example address is fake; GitLab is, regrettably, not hosting your project there.

  1. Open a terminal in the folder you want to track.
  2. Initialize Git and make the first commit:
$ git init
$ git add README.md
$ git commit -m "Initial commit"
$ git branch -M main

If there is no README.md yet, create one or add a file that already exists instead.

  1. Connect the GitLab project and publish the branch:
$ git remote add origin git@gitlab.example.com:group/project.git
$ git push -u origin main

Action 2
Clone an existing repository

Cloning downloads a project and sets up its remote connection. Copy the clone URL from the project page on GitLab. It is the project-sized version of "make me a copy".

$ git clone git@gitlab.example.com:group/project.git
$ cd project

Use the actual folder name created by git clone in the cd command.

Action 3
Pull the latest changes

Before you start working, make sure you are on the branch you intend to update. Then download and integrate its latest changes. Future-you appreciates the head start.

$ git status
$ git pull
A tiny bit of preventionRun git status first. If you have uncommitted work, commit it or save it temporarily before pulling. Your unsaved changes do not enjoy surprises.

Action 4
Make a change, commit and push

A commit saves a snapshot locally. Pushing sends your commits to GitLab so others can access them. Commit first; announce your masterpiece to the world second.

$ git status
$ git add path/to/your-file
$ git commit -m "Describe your change"
$ git push

Replace the file path and commit message with details about your work. To stage all current changes, use git add . instead, after checking git status.

Your future self says thanksMake small commits with clear messages. Check the staged files with git status before committing. "Stuff" is not a helpful commit message, even if it is technically accurate.

Action 5
Undo a mistake (without making it a sequel)

Choose the command based on what you want to undo. These actions are different: revert adds a new commit, while restore changes files in your working folder. Read twice, undo once.

Undo a commit that has already escaped into the world

Use git revert to create a new commit that reverses an earlier commit. This is the safer choice for commits already pushed or shared with others.

$ git log --oneline
$ git revert COMMIT_ID
$ git push

Replace COMMIT_ID with the identifier shown by git log.

Discard uncommitted changes to a file

This really does discard workgit restore overwrites your uncommitted changes to the named file. Check the file first and make a backup if you may need the changes. Git does not keep a sentimental scrapbook.
$ git restore path/to/your-file

Restore one file from an earlier commit

This puts that version of the file into your working folder. Review it, then commit the change if you want to keep it.

$ git log --oneline
$ git restore --source=COMMIT_ID -- path/to/your-file
$ git status
Tips & fixes

When Git gets dramatic

Look here when something unexpected happens. Pause before trying more commands, read the full error message, and check git status. Avoid deleting files or forcing a push until you know what is happening. Panic is not a Git command (and it has terrible error messages).

Conflicts: Git needs a human opinion

A conflict happens when Git cannot automatically combine changes to the same part of a file. Your changes and the incoming changes both need to be reviewed. Git is asking you to referee, not to pick a fight.

  1. See which files need attention:
$ git status
  1. Open each conflicted file. Conflict markers look like this:
<<<<<<< HEAD
Your version
=======
Incoming version
>>>>>>> branch-name
  1. Edit the file to keep the right content, and remove all conflict markers.
  2. Stage the resolved file and finish the merge:
$ git add path/to/resolved-file
$ git status
$ git commit

Review the result before pushing. If Git says a rebase is in progress, do not run git commit; after resolving and staging, use git rebase --continue instead.

Not sure which version to keep?Ask a collaborator before removing either side. You can also compare the changes in your editor's source control view.

The terminal editor appeared. Nobody panic.

Git may open a terminal editor when it needs a commit message. If the editor is Vim, press Esc first, then type one of these commands and press Enter. Yes, Vim can feel like a room with no visible door. There is a door:

  • :wq saves and exits. Use this to keep the commit message.
  • :q! exits without saving. Use this to cancel editing the message.
RememberVim commands are typed after pressing Esc. They will not appear in the file itself.

Forgot to pull first? It happens.

If your push is rejected because the remote has new commits, your local commits are not lost. No need to throw your laptop into the lake. First make sure your local work is committed, then integrate the remote changes:

$ git status
$ git pull --no-rebase
$ git push

If the pull reports a conflict, resolve it using the steps above, then push. If you have uncommitted changes, commit them before pulling, or ask for help if you are unsure.

Do not force-push to fix thisgit push --force can overwrite commits on the shared repository and affect your collaborators. That is a spectacularly efficient way to make it everyone's problem.
