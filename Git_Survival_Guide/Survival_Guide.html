Action
Create a new repository

Create an empty project on GitLab first, and uncheck the README.md. Replace the example URL with the SSH URL shown by GitLab..

  1. Open a terminal in the folder you want to track.
  2. Initialize Git and make the first commit:
$ git init
$ git add .
$ git commit -m "Initial commit"
$ git branch -M main
  1. Connect the GitLab project and publish the branch:
$ git remote add origin git@gitlab.example.com:group/project.git
$ git push -u origin main

Action
Clone an existing repository

Cloning downloads a project and sets up its remote connection. Copy the clone URL from the project page on GitLab. It is the project-sized version of "make me a copy".

$ git clone git@gitlab.example.com:group/project.git
$ cd project

Use the actual folder name created by git clone in the cd command.

Action
Pull the latest changes

Before you start working, make sure you are on the branch you intend to update. Only this one will be updated.

$ git pull
A tiny bit of preventionRun git status first. If you have uncommitted work, commit it or save it temporarily with git stash before pulling.

Action
Make a change, commit and push

Add to the staging area files you want to include before committing. A commit saves a snapshot locally. Pushing sends your commits to GitLab so others can access them.

Replace the file path and commit message with details about your work. To stage all current changes, use git add . instead of git add path/to/your-file.

$ git add path/to/your-file
$ git commit -m "Describe your change"
$ git push
For your future selfMake small commits with clear messages. Check the staged files with git status before committing. "Stuff" is not a helpful commit message, even if it is technically accurate.

Action
Create a branch and switch to it

A branch lets you work on a new feature or fix without touching main until it is ready. Creating and switching happen in a single command:

$ git switch -c feat/my-feature
$ git branch

git branch lists your local branches; the one marked with * is where you are right now.

Name it wellUse a prefix like feat/ or fix/ followed by a short description, e.g. feat/new-analysis. One branch, one task, and keep branches short-lived.

Action
Switch between branches

$ git switch main
$ git switch -

git switch - takes you back to the branch you were on before, handy when bouncing between main and your feature branch.

Uncommitted changes follow youChanges you have not committed travel with you when you switch branches, and sometimes Git will refuse to switch to avoid losing them. Commit first, or park them with git stash.

Action
Publish and merge your branch

The first push of a new branch needs the -u option to link it to GitLab. After that, a plain git push is enough.

$ git push -u origin feat/my-feature

When the work is ready, bring it into main. Always update main first, so you merge on top of the latest state:

$ git switch main
$ git pull
$ git merge feat/my-feature
$ git push origin main

Once merged, the branch has served its purpose. Delete it locally to keep the branch list tidy (you can also delete it on GitLab):

$ git branch -d feat/my-feature
Merge going wrong?You can cancel a merge at any time before committing with git merge --abort. If Git reports conflicts, follow the steps in the Conflicts section.

Action
Go back to an old commit

Choose the command based on what you want to undo. These actions are different: revert adds a new commit, while restore changes files in your working folder. Read twice, undo once.

Undo something that you have already committed

Use git revert to create a new commit that reverses an earlier commit. This is the safer choice for commits already pushed or shared with others.

$ git log --oneline
$ git revert COMMIT_ID
$ git push

Replace COMMIT_ID with the identifier shown by git log.

Discard uncommitted changes to a file

This really does discard workgit restore overwrites your uncommitted changes to the named file. Check the file first, and make a backup with a commit, a stash, or a new branch if you may need the changes.
$ git restore path/to/your-file

You can also restore all files in the working directory by omitting the file path:

$ git restore .

Restore one file from an earlier commit

This puts that version of the file into your working folder. Review it, then commit the change if you want to keep it.

$ git log --oneline
$ git restore --source=COMMIT_ID -- path/to/your-file

Tip
Having knowledge on what you did with git status and git log

When something unexpected happens, pause the command roulette and check what Git sees. git status shows your branch and local changes; git log shows the recent commit history.

$ git status
$ git log --oneline --graph --decorate -10

Tip
Conflicts: Git needs a human opinion

A conflict happens when Git cannot automatically combine changes to the same part of a file. Your changes and the incoming changes both need to be reviewed. Git is just asking you to tell him what to keep.

  1. Open each conflicted file. Conflict markers look like this:
<<<<<<< HEAD
Your version
=======
Incoming version
>>>>>>> branch-name
  1. Edit the file to keep the right content, and remove all conflict markers.
  2. Stage the resolved file and finish the merge:
$ git add path/to/resolved-file
$ git status
$ git commit

Review the result before pushing. If Git says a rebase is in progress, do not run git commit; after resolving and staging, use git rebase --continue instead.

Tip
The terminal editor appeared. Suddenly, the keyboard makes no sense, and Escape is nowhere to be found.

Git may open a terminal editor when it needs a commit message. By default the editor is Vim, press Esc first, then type one of these commands and press Enter.

  • :wq saves and exits. Use this to keep the commit message.
  • :q! exits without saving. Use this to cancel editing the message.

If you have never used vim before, I highly recommend you to change the default text editor. For that you can run:

$ git config --global core.editor "my_new_editor"

If you use VS Code (recommended), set it with: "code --wait". Otherwise "notepad" on Windows or "nano" in the terminal are easy options too. RStudio, however, does not work here: it does not make Git wait for you to finish, so commits get aborted with an empty message.

Tip
Committed on the wrong branch? It happens too.

You made commits directly on main instead of a feature branch. As long as you have not pushed yet, move those commits to a new branch and put main back to the state on GitLab:

$ git branch feat/my-work
$ git switch main
$ git reset --keep origin/main

Your commits are now safe on feat/my-work, and main matches the remote again. Switch to the new branch and carry on.

Only if you have not pushedIf the commits are already on GitLab, do not rewrite the shared history. Revert them instead, see the Undo section.

Tip
Need to switch branches with uncommitted work? Stash it.

The stash is a shelf for work in progress: it saves your uncommitted changes and gives you a clean folder, so you can switch branches or pull safely.

$ git stash
$ git switch other-branch

Back on your branch, take the changes off the shelf:

$ git stash pop
Lost track of your stashes?git stash list shows everything on the shelf, and git stash show -p previews the most recent one.

Tip
Forgot to pull first? It happens.

If your push is rejected because the remote has new commits (usually you forgot to pull, or someone else is working on the same branch), your local commits are not lost. First make sure your local work is committed, then integrate the remote changes:

$ git status
$ git pull --no-rebase
$ git push

If the pull reports a conflict, resolve it using the steps above, then push.

Do not force-push to fix thisgit push --force can overwrite commits on the shared repository and cause other issues.
